# 时延基准

一条命令复现 README 里的性能数字：

```bash
pip install -e ".[dev]"
python benchmarks/latency.py                  # 人读
python benchmarks/latency.py --json           # 机读，可进 CI 做趋势对比
python benchmarks/latency.py --rounds 2000    # 更多采样
```

## 口径

**这台机器上的实测值**（Windows 11 / Python 3.13 / 单进程 / mock 执行器）：

| 阶段 | n | P50 | P95 | 说明 |
|---|---|---|---|---|
| 规划（规则） | 500 | 0.01 ms | 0.02 ms | 正则解析，不含模型调用 |
| 安全闸门（7 条策略） | 500 | 0.01 ms | 0.02 ms | 纯 CPU |
| 端到端 | 50 | 10.0 ms | 12.6 ms | 真 SQLite + 真审计文件 + mock 执行器 |

| 并发 | 结果 |
|---|---|
| 16 个任务 | 串行 158 ms → 并发 145 ms（**1.09×**） |

## 这组数字说明什么

**编排层不是瓶颈。** 规划和闸门加起来 0.02 ms，端到端的 10 ms 几乎全在
SQLite 写入与审计落盘上。接入真实 LLM 后，模型延迟（通常 500~3000 ms）会
完全盖过本地开销——这意味着**优化方向应该是缓存高频意图、减少模型往返，
而不是去抠策略链的微秒级开销**。

**并发收益有限，原因明确。** 16 个任务并发只有 1.09×，不是「并行没写好」，
而是两处真实串行：

1. 物理动作由 `asyncio.Semaphore(1)` 强制串行——一台机器人同一时刻只能执行
   一个动作序列，这是物理约束，加机器才能解决；
2. SQLite 是单写者，所有任务的状态写入排队。

所以「多任务并发」的收益上限被这两处锁死。要提升吞吐，正确的做法是换
PostgreSQL（解除写锁）和增加机器人（解除物理串行），而不是继续压榨 asyncio。

## 这组数字不能说明什么

- **不是 ROS2 的延迟**。`/cmd_vel` 发布、odom 回调、DDS 发现都不在测量范围内；
  真机链路的延迟要比这高一个量级。
- **不是 LLM 的延迟**。规则规划器 0.01 ms，模型调用是另一回事；两者混在一起
  报会让数字失去意义。
- **不是吞吐上限**。这是单进程、单机器人的数据，`max_concurrent_tasks` 默认 4，
  没有做压力测试。
- **换机器就会变**。绝对值受 CPU 与磁盘影响，**比值和瓶颈位置**才是可迁移的结论。
